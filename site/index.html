Use the smallest useful thing

Not every note needs a kit.

Loadout manages how context is composed and installed. Your agent harness still decides how that context is discovered and used.

PLAIN INSTRUCTIONS

A few enduring rules

Keep repository facts and everyday conventions in AGENTS.md or CLAUDE.md. Editing one small file yourself may be all you need.

A SKILL

A task-shaped workflow

Put a focused procedure in SKILL.md, with a clear description and supporting references. The harness can load it when relevant rather than treating the whole procedure as standing guidance.

A LOADOUT KIT

A repeatable choice

Use a kit when you want questions, conditional content, multiple outputs, shared authoring, consistent destinations, or independent repository and global intent.

Organization, not magic compression. Linking files can reduce duplicate files on disk. It does not, by itself, reduce model context or guarantee that a harness will load content only once.

Get started, locally.

Loadout currently runs from the repository with Bun. It is not an npm-published CLI to install with npx. Use mise for the runtimes pinned in .mise.toml in the checkout. 

mise trust
mise install
mise exec -- npm install
mise run dev

Run these commands in the Loadout checkout. To configure another project, point Loadout at it explicitly: 

mise exec -- npm run dev -- --repo /path/to/project

Build and inspect

mise run build
mise exec -- bun dist/cli.js --help
mise exec -- bun src/cli.tsx status

Know what runs

OpenTUI’s Solid integration runs on Bun. npm manages the local dependency lockfile. status is read-only and returns nonzero for source or output drift; it does not repair files.

Developing Loadout? Use mise run check. Architecture is described in the reference.

A five-minute orientation

Browse. Configure. Review.

Try the built-in Project context kit for a complete example. Looking around and editing a draft do not install anything.

The application also offers a dismissible first-launch walkthrough. Replay it with --walkthrough at launch, or ? in the TUI when no form is open. Viewing it does not apply kits or change installation intent.

  1. Find a kit

    Start on Catalogs. Highlight Loadout to see its kits, then press Space to browse. Highlight Project context to preview its instructions, skill, and optional note.

    Catalogs / Loadout
    › Project context
    Questions → instructions + skill + optional file

    Conceptual illustration, not a terminal screenshot. Repo discovers your project’s .loadout/kits/*.yaml automatically.

  2. Choose where it belongs

    Press Space to configure. Start with Repository for project-specific context. Answer the project-name question, then decide whether deployment guidance and the optional note are useful.

    Install where?
    ● Repository   ○ Global   ○ Both
    What is this project called?
    My project

    The preview changes with your answers; excluded fragments are gray. An open kit keeps navigation inside its own form. Use the explicit Cancel action to discard its edits.

  3. Accept a draft, not a write

    Choose Accept, or press Esc, to stage the kit. Required questions must be answered first. Enter finishes typing an answer without accepting the whole kit.

  4. Read the review

    Switch to Review with Tab. Inspect the exact resolved paths, generated text, diff, and any other affected repositories. The default action is Keep editing.

    Review / planned changes
    + instruction fragments
    + managed skill files

    ● Keep editing   ○ Apply changes

  5. Apply only when ready

    Explicitly focus Apply changes, then press Space. That is the final confirmation. Loadout saves intent and answers even if there are no file changes. Start or refresh your agent harness as its own discovery rules require.

Keyboard field guide

Scope colors reinforce labels: Repository is blue, Global gold, Both lavender, and Not installed gray. Instructions use sage, skills lavender, and other files blue. Excluded content is gray; labels and markers do not rely on color alone. Highlight a file in Review to inspect its colored diff.

↑/↓ or j/k move between rows; lists wrap. ←/→ or h/l focus horizontal options; Space selects or toggles. Focus is distinct from selected radio/check markers, and options wrap on narrow terminals.

Landing on a text input starts typing; Vim keys and q are then literal text. Up/Down can leave the input. Text stays visible below its label; question help is muted and italic. Accept/Cancel share one horizontal action row.

Tab/Shift+Tab cycle Catalogs, Installed, Review, and Settings after an open form is finished. PgUp/PgDn scroll details. Outside a kit, Esc goes back or stops catalog input. r refreshes sources and drift when no form is open.

Press q twice to exit: once to open confirmation, again to exit. Esc stays; Space does not confirm exit. Ctrl+C opens the same prompt.

Kit previews merge instruction fragments into one section; skills show their names and supporting files. Review retains drafts when you choose Keep editing, returns to Installed, and refreshes the plan next time.

Intent is not a destination

One kit. Two kinds of home.

Repository

Keep context in this project. Good for a team’s conventions and project-specific answers.

Global

Keep context in your user configuration, available across projects that your harness discovers.

Both

Retain both intentions, but materialize only the global copy while it exists. Repository intent becomes a fallback.

Adding a global kit suppresses redundant copies in all known repositories without forgetting their intent. Removing the global kit restores those repository copies with each project’s saved answers. Review includes every affected repository, not just this session’s project. Tab transitions refresh scope saved by other sessions.

Choose Repository to remove global intent but keep this project’s fallback. Not installed clears global intent and this project’s repository intent, not other projects’ intent.

Locations & copies

Settings controls ordered repository/global instruction and skill locations. Defaults cover Codex, Claude, and OpenCode, including their shared repository instruction destination. Explicit Codex and XDG configuration homes are respected.

Copy mode writes independent files. Link mode stores real managed files in the first, primary location and links individual managed files in later locations—not whole skill roots.

Generated-file ignores

None is the default. Shared maintains a marked section in .gitignore; Local uses Git’s private exclude file. Rules cover exact managed repository files and links only.

Tracked files stay tracked. Loadout reports and skips ineffective rules; it never untracks files or changes index flags. Settings and rule changes still require Review and Apply.

A helpful second pair of eyes

Let an agent help you choose.

Give your agent the Loadout checkout and a concrete goal. Its question tool can gather your answers; the CLI provides structured discovery, planning, and guarded apply without driving the terminal UI. 

Help me configure Loadout for this repository.
Run guide, then inspect --json from the Loadout checkout.
Ask which harnesses I use, my project conventions, and whether each
kit belongs in this repository or my global configuration.
Inspect existing instruction and skill files before proposing changes.
Prefer a small kit or plain instructions when that is enough.
Show the exact plan, destinations, and conflicts; wait for my approval
before any apply. Do not put secrets in saved answers.
  1. Discover: inspect the current command contract and available kits; do not assume a published package exists.
  2. Ask: agree on scope, destinations, and the answers that control conditional content.
  3. Preview: compare generated content and existing files; explain external provenance and harness caveats.
  4. Confirm: obtain approval of the actual current plan, then apply through Loadout’s guarded workflow. 
mise exec -- bun src/cli.tsx guide
mise exec -- bun src/cli.tsx inspect --json --repo /path/to/project
mise exec -- bun src/cli.tsx plan --request request.json --json --repo /path/to/project
# Only after the human approves this exact review token:
mise exec -- bun src/cli.tsx apply --request request.json --review-token TOKEN --approve --json --repo /path/to/project

The agent must never self-confirm. --approve attests to actual human approval of the exact review token. Apply rebuilds the plan and rejects changed context; a new token requires renewed review and approval. Registering external catalogs needs separate consent.

Less standing prose.
Not a token-savings promise.

Moving a task procedure out of standing instructions and into a skill changes when a harness may load its body. The description still has a discovery cost. Invoking the skill loads more content; reading its references loads more again.

Methodology, exclusions, and reproducibility

Measurements use pinned upstream UTF-8 text retrieved 19 October 2026. Bytes use Buffer.byteLength; words are maximal non-whitespace runs (/\S+/gu). Lines are LF-separated logical lines, with no phantom empty line after a final LF; empty text has zero lines. Unicode characters, also present in the raw data, mean code points, not grapheme clusters.

Frontmatter includes delimiter lines and their LF. Body means everything after the closing delimiter LF, including the following blank line. Descriptions are parsed YAML scalars: Ponytail’s folded description retains its trailing LF, so its discovery string has three lines, not two.

Full-file counts exclude license files, SOURCE notices, and Matt’s Codex UI/policy metadata; these installed supporting files have separate records in the data. The selected directories contain no required external supporting Markdown, scripts, or binaries. If references or notices are read by a host, their contents must be added. Do not confuse installed disk totals with prompt text.

Actual paths, wrappers, permissions, metadata budgets, hidden/always-active policies, system prompts, tools, history, truncation, and retained activations differ. No tokenizer was used: bytes and words are not runtime tokens, latency, cost, or a benchmark.

Download measurement and provenance JSON · Complete file inventory: catalog/external-sources.json in the checkout. The downloadable JSON and HTML tables are maintained static presentations, not automatically generated by the measurement command.

  1. Run mise exec -- bun catalog/external/measure.ts offline. It derives metrics from vendored text and regenerates the canonical catalog/external-sources.json, curated kit YAML, and SOURCE notices, without downloading or executing upstream code.
  2. Manually refresh site/source-measurements.json from that canonical inventory, and update all HTML measurement tables, assumed activation cases, totals, citations, and dated references together.
  3. Review the synchronized presentation against the pinned sources, licenses, hashes, arithmetic, and methodology before sharing it. The command does not update the site extract or HTML.
Native profiles, native rules

A subagent is not just a skill.

A skill packages a workflow; a subagent is a harness-specific assistant profile with its own invocation and context behavior. Installing a definition does not launch it, guarantee delegation, or make the same permission controls portable across harnesses.

Codex

Follow Codex’s native agent configuration and delegation support. Do not assume Claude frontmatter or OpenCode permission rules translate directly.

Native documentation ↗

Claude Code

Subagents use native definitions and tool/permission policies. Skills can also use a forked context; that is a Claude-specific feature, not a portable skill guarantee.

Native documentation ↗

OpenCode

Subagents run in fresh child sessions. Parent permissions control launching; children use their own configured permissions. Native profiles use mode: subagent.

Native documentation ↗

Loadout’s type: agent contribution serializes separate native profiles for the selected harnesses. They participate in the same scope, snapshot, review, conflict, and recovery lifecycle as other managed outputs. Native agents are not cross-harness symlink copies.

Omitted model/tool settings inherit host behavior, not a least-privilege sandbox. Delegation may isolate a task’s working context, but child prompts, repeated instructions, and returned results still have costs; it is not free context or automatic token savings.

Share the recipe, not everyone’s answers

Start with one YAML file.

Commit kit YAML directly under .loadout/kits/. The automatic Repo catalog needs no index and no registration; each teammate chooses kits and answers independently. 

id: project-note
name: Project note
description: Add a short project reminder.
questions:
  - id: project-name
    label: What is this project called?
    type: input
    default: My project
    required: true
outputs:
  - type: instructions
    content: |
      You are working on {{project-name}}. Follow this repository's conventions.

Kits ask input, boolean, select, and multi-select questions. Conditions include content declaratively; interpolation changes content only, never paths. Kits do not run hooks, execute code, or invoke subagents.

External catalogs

An external catalog is a strict JSON index pointing at self-contained kit YAML. Register a local path or HTTPS URL; registration is a user-wide source reference, not an installation.

Provenance is part of a useful kit

Before sharing an upstream skill, verify the author and repository, pin a commit, inspect every supporting file, and confirm that its license permits redistribution. Preserve notices and distinguish original text from adaptations. Publicly readable does not mean freely redistributable.

Review instructions as carefully as code: they can persuade an agent to use tools even though Loadout never executes the kit. Ambiguous source names are not enough to establish identity. Do not install guessed content or imply an endorsement.

Curated selections include Matt Pocock’s questionnaire (MIT), Anthropic’s frontend design (Apache-2.0), and DietrichGebert’s Ponytail core skill (MIT). They include the complete selected skill directories, licenses, and source notices—not entire upstream repositories or Ponytail’s hooks/plugins. Matt’s Codex policy metadata is preserved. Ponytail’s requested modes and session persistence depend on the host and never override user constraints.

Read pinned commits and hashes, source measurements, and first-party attribution. Installing a kit does not run its skill; upstream authors do not thereby endorse Loadout.

A review is a boundary

Keep your work yours.

Detect, don’t silently replace

Saved definitions and answers keep installed kits usable when sources disappear or become invalid. A changed source never silently updates your installation. Modified or missing managed output is a separate conflict.

Use Installed → Use catalog update for an explicit update, answer new or incompatible questions, then review and apply. User instruction text outside managed blocks is preserved.

State is local, not secret storage

~/.loadout/state.json records registrations, intent, answers, snapshots with source provenance, known repositories, and managed-file records. Answers are plain text. Never enter secrets.

Changing global scope can touch every known repository. An inaccessible project or conflicting edit can block a safe apply.

Interrupted apply? Close other sessions and verify no apply is running before manually removing only ~/.loadout/lock. Keep journal.json: the next launch uses it for recovery. If files changed after interruption, stop and inspect rather than overwriting them.

Apply checks concurrent edits and uses a write-ahead journal for rollback. Atomic replacement preserves permission bits, not a promise of extended attributes, ACLs, or hard-link relationships. Recovery is not a backup.
